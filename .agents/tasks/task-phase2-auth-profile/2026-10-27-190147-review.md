# Phase 2: Provider Auth, Registration, Profile, and Dashboard

Phase 2 wires the complete provider-side auth and profile flow on top of Firebase Auth and Firestore. The change adds the services layer (auth.ts, firestore.ts, geocoding.ts), three new hooks, two new UI components (SkillPicker, AvailabilityToggle), and fully implements Register, Login, Dashboard, and EditProfile pages using React Hook Form + Zod. LocationInput is migrated from Google Maps (billing required) to Nominatim. TypeScript compiles clean (`tsc --noEmit` exits 0) and the Vite build passes (chunk size warning only, not an error).

Watch for: (1) **confirmed** — `RegisterPage` step 2 uses two `<h1>` elements on the same page (one per step), which is a minor but real heading-hierarchy issue. (2) **confirmed** — the `mapAuthError` function in `RegisterPage` falls through to a hardcoded `'Something went wrong'` instead of surfacing `err.message` for unknown error codes, losing useful debug info. (3) **possible** — Nominatim's ToS requires a valid `User-Agent` with contact info; `'Djema/1.0'` alone may get rate-limited in production without an email address appended.

**Verdict**: APPROVED

---

## High-level view

The services layer isolates all Firebase access cleanly. `auth.ts` owns the four required auth functions; `firestore.ts` owns all six Firestore helpers and re-exports `GeoPoint` so pages never touch `firebase/firestore` directly. No page component imports from Firebase directly — confirmed via grep. The `useAuth` hook no longer exports `signOut`; `Navbar` and pages import it from `@/services/auth` as required.

`LocationInput` is a complete replacement: Google Maps type declarations, script injection, and the Autocomplete listener are gone. Nominatim is called via `@/utils/geocoding` with a 500ms debounce, outside-click handling, and accessible `listbox`/`option` ARIA roles. The `User-Agent` header is set to `'Djema/1.0'`, which satisfies the policy requirement minimally.

The two-step registration flow separates Firebase Auth account creation (step 1) from Firestore profile writing (step 2), storing the `uid` in local state between steps. The Google path also reaches step 2 correctly. Error mapping covers the common Firebase error codes; unknown codes fall back to a hardcoded string rather than surfacing `err.message`.

`AvailabilityToggle` is fully accessible: `role="switch"`, `aria-checked`, keyboard handling for Enter and Space, focus ring, and a loading state via `Loader2`. The optimistic update in `DashboardPage` reverts on Firestore failure. `SkillPicker` correctly caps selection at 10 and uses `aria-pressed` on chips.

Firestore rules cover all four required collections. The `matches` write rule tightens the plan's `write: if isAuth()` to `write: if isAuth() && request.resource.data.providerUid == request.auth.uid`, which is a strict improvement.

<details>
<summary>Issues (3)</summary>

1. **Dual h1 on RegisterPage** — Step 1 and Step 2 each render an `<h1>`. Since they are both mounted within the same `<main>`, whichever step is active produces a valid single `<h1>`, but screen reader users navigating by heading will encounter a heading structure that changes in-place without a page navigation signal. Change step 2's heading to `<h2>` or add an `aria-live` region to announce the step transition.

2. **mapAuthError drops err.message for unknown codes** — In `RegisterPage.tsx`, `mapAuthError(code)` returns `'Something went wrong. Please try again.'` for any unrecognised Firebase error code. The login page's version (`mapAuthError(code, fallback)`) passes `err.message` as the fallback, which is better. Align `RegisterPage`'s version to accept and use `err.message` as the fallback for unknown codes.

3. **Nominatim User-Agent may trigger rate-limiting** — The Nominatim usage policy ([https://operations.osmfoundation.org/policies/nominatim/](https://operations.osmfoundation.org/policies/nominatim/)) requires a valid contact email in the `User-Agent` or a separate `From` header. `'Djema/1.0'` satisfies the identification requirement but not the contact requirement. Append a contact address: `'Djema/1.0 (contact@example.com)'` or add a `From` header.

<details>
<summary>Details</summary>

### Two `<h1>` tags in a single RegisterPage render

Both the step-1 and step-2 branches render `<h1 className="font-display ...">`. Since only one is visible at a time (conditional render), the DOM never has two simultaneous `<h1>` elements — the document heading structure is technically valid. However, the step transition happens in-place with no navigation event, so assistive technologies that cache the page title won't announce the change to "Tell us about yourself". This is a minor accessibility gap, not a blocker, but worth fixing before the public launch.

### Error message loss in RegisterPage's mapAuthError

`LoginPage.tsx` passes `err.message` as the second argument to `mapAuthError`, so unknown Firebase errors surface their actual message. `RegisterPage.tsx` calls `mapAuthError(code)` with no second argument, so any error code outside the four handled cases returns the generic string. This makes it harder to diagnose auth issues in production. The fix is one line — change the signature to accept and use a fallback.

### Security: matches write rule exceeds the plan

The plan specified `write: if isAuth()` for `matches`. The implementation tightens this to `write: if isAuth() && request.resource.data.providerUid == request.auth.uid`, preventing a provider from writing a match document with another provider's UID. This is a strict improvement — confirmed.

### Auth import boundary

No page or hook imports directly from `firebase/auth` or `firebase/firestore`. `useAuth.ts` imports only `onAuthStateChanged` from `firebase/auth`; all auth operations go through `@/services/auth`. Confirmed via grep.

### Geocoding: Nominatim integration

The `geocodeLocation` function validates the response shape before casting, throws typed errors on non-OK status and non-array responses, and returns an empty array (not an error) on no results. The `User-Agent` header is present. The contact-info gap noted in the Issues list is the only open item.

### Build verification

`npx tsc --noEmit` exits 0. `npx vite build` exits 0 with a chunk size warning (774 kB bundle) that reflects lucide-react being bundled monolithically — pre-existing concern, not introduced in this PR.
