# Phase 2: Provider Auth, Registration, Dashboard, and Profile

Three commits add the complete auth and provider-profile layer to the Djema SPA: a services/utilities foundation (auth.ts, firestore.ts, geocoding.ts, category types), then the full UI layer (SkillPicker, AvailabilityToggle, LocationInput replacement, two-step RegisterPage, LoginPage, DashboardPage, EditProfilePage), followed by a small integration-fix commit. The approach correctly centralises all Firebase access behind service wrappers and keeps page components clean of direct SDK calls. Nominatim fully replaces the billing-gated Google Maps integration.

**Watch for:** `throw` inside `onSnapshot` error callbacks (lines 76–77 and 102–103 in firestore.ts) is a confirmed bug — the thrown error escapes into an unhandled promise and will crash the browser console silently instead of surfacing to calling code. The `err as FirebaseError` cast in LoginPage and RegisterPage is confirmed unsafe when the caught error is not actually a Firebase error; `instanceof` narrowing is needed. The `matches` collection `allow write: if isAuth()` rule is confirmed overly permissive — any authenticated user can write any match document.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The service layer (FEAT-001) is cleanly designed: auth.ts owns the four required functions, firestore.ts centralises all Firestore CRUD behind typed signatures with no `any`, geocoding.ts validates the Nominatim response structure before returning it. GeoPoint is re-exported from firestore.ts so pages never need to reach into firebase/firestore directly.

The UI layer (FEAT-002) satisfies the design-system rules consistently: font-display on all h1/h2/h3, font-sans elsewhere, rounded-lg on all buttons, no card borders, no emojis, Lucide icons only. React Hook Form + Zod is used on all three forms (Register step 1 and 2, Login, EditProfile) with field-level and form-level error display.

The `onSnapshot` error handler pattern in firestore.ts throws inside a synchronous callback delivered by the Firebase SDK, which cannot propagate to callers. This affects both `subscribeToProvider` and `subscribeToCategories`. The error is discarded silently, so a Firestore permission denial or network failure during a real-time subscription will produce no user-visible feedback.

The auth flow has a confirmed type-safety gap: both pages catch errors in auth functions and immediately cast `err` to `FirebaseError`, but the wrapped service functions can throw plain `Error` objects (e.g., network errors before the Firebase SDK is reached), making `.code` undefined and falling through to the default error message branch. This is a latent bug rather than a crash risk.

The Firestore security rules cover all four collections. The `matches` write rule (`if isAuth()`) lets any authenticated provider overwrite any match document, not just their own. Since Cloud Functions are deferred, this is a documented trade-off in the plan, but it means any provider can manipulate match results for other providers' requests.

No TypeScript errors (`tsc --noEmit` exits 0) and the Vite production build completes cleanly (chunk-size warning only, not an error). Both FEAT-001.json and FEAT-002.json report `status: "completed"`.

<summary>Issues (3)</summary>

1. **onSnapshot throws into void** — `throw new Error(...)` inside the onSnapshot error callback in `subscribeToProvider` (line 76) and `subscribeToCategories` (line 102) does not propagate to callers; the error is silently discarded. Replace with a passed-in error callback parameter or call `console.error` and invoke the existing callback with `null`/`[]`.

2. **Unsafe FirebaseError cast** — `err as FirebaseError` in LoginPage (lines 49, 60) and RegisterPage (lines 92, 104) bypasses TypeScript's type narrowing. If the wrapped service function throws a plain `Error`, `code` will be `undefined`, falling through to the default message. Use `instanceof` checks: `if (err instanceof Error && 'code' in err)` before reading `.code`.

3. **Matches write rule too permissive** — `allow write: if isAuth()` on `/matches/{requestId}` lets any authenticated user overwrite any match document. Add `isOwner(requestId)` or restrict to the match's `providerUid` field to limit writes to the affected provider.

<details>
<summary>Details</summary>

### onSnapshot error handlers throw into void

Both real-time subscription functions — `subscribeToProvider` and `subscribeToCategories` — pass an error callback to `onSnapshot` that does `throw new Error(...)`. The Firebase SDK delivers this callback synchronously from an internal microtask; the thrown error escapes into an uncaught promise rejection rather than propagating to the call site. The caller's `useEffect` has no try/catch around `subscribeToCategories`, so a categories subscription failure (permission denied, offline) produces no visible feedback and no unsubscribe. The fix is either to accept an `onError` callback parameter alongside the existing `callback`, or to call the existing callback with an empty array / null and log the error.

### FirebaseError cast in page components

`import type { FirebaseError } from 'firebase/app'` is the correct type-only import (no runtime value), so the pages can't use `instanceof FirebaseError`. The current code casts the caught value: `const code = (err as FirebaseError).code ?? ''`. This is safe when the error originates from Firebase Auth, but the service functions in auth.ts don't wrap errors — they let Firebase errors propagate directly, so in practice the cast nearly always works. However, if a network interceptor or test harness throws a plain `Error`, `code` will be `undefined` and the cast silently falls through. The safer pattern is `const code = err instanceof Error && 'code' in err ? (err as { code: string }).code : ''`.

### Matches write rule

`requestId` in the matches collection is a request document ID, not a provider UID, so `isOwner(requestId)` doesn't apply directly. A minimal tightening without Cloud Functions: restrict writes to documents where `request.resource.data.providerUid == request.auth.uid` — catching the pattern when a provider writes their own result. The plan documents this as a Phase 2 trade-off, but the field-level check is a one-liner that doesn't require rearchitecting anything.

</details>
